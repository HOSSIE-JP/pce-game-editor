## Stage 1: 企画とシナリオ設計

最初に次を出し、物語の成立を確認する。ユーザーが一括生成を指定していなければJSONはまだ作らない。

1. 一文ログライン
2. 作品の約束（何を楽しむ作品か）
3. テーマと、その反対意見または反証
4. 登場人物表
5. 始まり・中盤の転換・クライマックス・結末
6. シーン別ビート表
7. 分岐表
8. 想定message数とscene数
9. 使用予定の既存アセット
10. 不足素材

シーン別ビート表には次を含める。

| 項目 | 内容 |
|---|---|
| scene仮ID | 英数字・`_`・`-` |
| 目的 | このsceneで変わること |
| 誰の欲求が前進するか | 行動主体 |
| 対立・障害 | 会話または出来事の摩擦 |
| 開示情報 | 観客が新しく知ること |
| 感情の入口→出口 | scene内の変化 |
| 選択・分岐 | 選択肢、結果、合流点 |
| 使用アセット | BG、sprite、BGM、SE、voice |
| 規模 | 想定message数 |

### 分岐設計

- 各選択肢が何を選んでいるかを一文で説明する。単なる正解・不正解にしない。
- 即時反応、後続への影響、合流点またはエンドを表にする。
- 変数が不要なら`choice.targetSceneId`だけで分岐する。
- 後から結果を参照する場合だけ`variableName`と`value`を使う。
- 同一scene内で短く分岐する場合はlabel系、会話量が増える場合はscene分割を選ぶ。
- 一本道の作品へ無理にchoiceを追加しない。

### シナリオ本文

- 台詞はキャラクターの欲求と状況から発生させる。設定説明だけを連続させない。
- 同じ情報をナレーションと台詞で重複させない。
- 各messageは一つの発話意図に絞り、17文字×表示行へ割りやすくする。
- キャラクター表で定めた一人称、呼称、知識範囲を機械的に点検する。
- 重要な伏線には回収sceneを、重要な選択には反応sceneを対応させる。

## Stage 2: アセット設計・生成

対象プロジェクトがある場合、`pce-assets.json`を型別に棚卸ししてから不足を出す。

```json
{
  "assets": [
    {
      "id": "bg_station_night",
      "type": "image",
      "name": "背景/夜の駅",
      "size": "224x136",
      "usage": "通常背景",
      "prompt": "anime visual novel background, quiet station platform at night, clear silhouettes, flat colors, minimal gradients, no text, 224x136"
    }
  ]
}
```

- asset planはScene JSONと分ける。
- IDは既存IDと衝突させず、小文字英数字・`_`・`-`を基本とする。
- 通常背景とイベントスチルは224×136を推奨する。全画面演出は256×224。
- イベントスチルの枚数と画風は作品入力で決める。入力がなければ、物語上の転換点だけを提案し、固定枚数を強制しない。
- 画像生成を行う場合は、構図案→生成→224×136または256×224の実ファイル確認→エディタ登録→確定ID取得の順に進める。
- 画像生成機能が使えない場合は、プロンプト、ネガティブ条件、構図、寸法、登録予定IDまでを納品する。
- 画像内へ台詞、UI、読ませる文字を描き込まない。
- 立ち絵は透明背景とし、表情・animationのROW構造をasset planへ記載する。口パクする通常ROWの直後に口パクROWを置く。
- 新規BGM/SE/voiceも型、用途、loop、再生媒体を明記する。
- 新規素材を`pce-assets.json`へ登録するまでは、Scene JSONでそのIDを参照しない。

### 音声後工程

- 台本確定前のmessageは`voiceAssetId: ""`とする。
- 台本確定後にIrodori-TTSバッチ等で一意な音声IDを採番する。
- 生成音声をADPCMとして登録し、本文と1対1対応を確認して`voiceAssetId`へ反映する。
- 台詞変更後は音声を再生成し、ID・本文・speakerの対応を再点検する。

## Stage 3: Scene JSON生成

1. 承認済みビートをsceneへ分割する。両対応ならHuCARDの4096 bytesを基準に小さく分ける。
2. 冒頭で必要な背景とspriteを表示する。
3. CD-DAを使う場合は、同sceneの初期画像ロード後にplayする。
4. messageを17文字×3行（話者あり）または4行（ナレーション）へ整形する。
5. 口パクするmessageだけへ`mouthSlot`を指定する。
6. 分岐参照と合流点を実IDで接続する。
7. 未登録asset IDと仮voice IDを除去する。
8. `version`、`settings`、`startScene`、全sceneを含むvalid JSON全文を保存する。
9. JSON parserを通す。
10. スキル同梱validatorを通す。

ユーザーが既存JSONを渡した場合は、そのドキュメントを正規化した完全版を返す。既存のtitle、system scene、デバッグ用comment等を削除するかはユーザーの指示に従い、作品固有のscene ID形式を勝手に変更しない。

## Stage 4: 検証とビルド

```powershell
node .grok/skills/author-pce-vn/scripts/validate-vn-project.mjs C:\path\to\project --media both
```

- validatorの`ERROR`は修正必須、`WARNING`は意図を確認する。
- CD検査は現行engineのnormalization、文字encoder、scene-pack codecを使う。
- HuCARD検査はプロジェクトの`assets`を一時ディレクトリへコピーしてsource生成し、4096-byte上限とHuCARD側文字・asset処理を確認する。
- 検査後も、対象メディアの通常buildを行う。
- 実行画面で背景位置、改行、選択肢、戻り先、口パク、sprite移動、AUTO、BGM/SE/voiceを確認する。

## Grokへの依頼例

```text
/author-pce-vn

新規の短編ビジュアルノベルを作成してください。
対象プロジェクト: C:\path\to\project
対象メディア: CD-ROM2とHuCARD
想定読了時間: 10分
ジャンル: [記入]
舞台: [記入]
テーマ: [記入]
登場人物: [名前、役割、性格、口調、呼称]
必須の出来事: [記入]
分岐方針: [一本道／短い分岐／複数エンド]
新規アセット: [許可範囲]
画像生成: [実施する／プロンプト案のみ／不要]
イベントスチル: [希望枚数、場面、画風]
音声: [なし／一部／フルボイス]

まずStage 1の企画、キャラクター表、シーン別ビート、分岐表、既存アセット使用表、不足素材だけを出してください。JSONはまだ生成しないでください。
```

Stage 1承認後:

```text
承認したシナリオ設計と、現在のpce-assets.json、pce-vn-scenes.jsonを正本にしてください。
不足画像を生成・登録できる場合は先に実施し、登録済みIDだけでScene JSONを作ってください。
その後、assets/pce-vn-scenes.jsonとして保存できるvalid JSON全文を生成し、--media bothで検証してください。
エラーを修正し、最後にJSON全文と検証結果を返してください。
```

## 出力品質チェック

- 固定の作品設定を混入していない。
- キャラクターの一人称、呼称、知識、口調が一貫している。
- 各sceneに目的と感情変化がある。
- 選択肢の意味と結果が区別できる。
- 未回収の必須伏線や到達不能sceneがない。
- 既存asset IDと型が正しい。
- 新規素材はasset planと登録工程を経ている。
- messageの行数・行長が表示枠内にある。
- Full BG、mouthSlot、CD-DA順序、HuCARD無音仕様を守っている。
- JSON parseとvalidatorが成功している。
- 実ビルド・実行確認が未実施なら、その残件を明記している。
